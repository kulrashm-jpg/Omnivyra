### 2a. W2A-4 design (observe first)

- `attributeAuthenticatedPrincipal({ userId, orgId?, source })` (`backend/services/requestContextPrincipal.ts`) is called after a successful authentication in `resolveUserContext`, on every allow branch of `enforceCompanyAccess`, at the end of `requireCampaignAccess`, and in `requireTenantAccess` (before its own `seedRequestContextFromRequest`).
- It mutates the **live** store object (`getMutableRequestContext()`), because a store swapped in with `enterWith` inside an awaited callee does not propagate to the caller (the reason `requireTenantAccess`'s seed never reached the gateway). Outside a request scope it is a no-op and never creates one.
- Rollout flag `ai-guard-principal` (`ROLLOUT_AI_GUARD_PRINCIPAL_MODE`, `_KILL`, `_TENANTS`, global `ROLLOUT_KILL_SWITCH`):
  - `shadow` (**default**): records `authPrincipal` only. No existing code reads it, so the guard, the AI cache (which derives tenant scope from `orgId`), logs and billing see exactly what they saw before. Counter `ai.guard.principal_attribution{source,mode,outcome}` once per request: `would_attribute` = the request would gain a user identity in the guard.
  - `enforce`: also fills context `userId` (never `orgId`) when not already set. Per-tenant promotion from `shadow` with `_TENANTS=<orgId,…>`.
  - `off` / kill: no-op.
- Safety: first user wins (a second, different user in one request ⇒ `conflict`, never re-attributed); an explicit upstream `userId` is never overwritten; the synthetic `content_architect` principal is never used as a rate-limit key; requests stay isolated (tested with two concurrent scopes).
- What it does not do: it does not measure *what would be throttled*. That needs a shadow evaluation inside `guardAiRequest` (SEC-D-owned) — see §6.1.

### 6.1 SEC-D — observe "would be throttled" inside `guardAiRequest`
`backend/services/ai/aiRequestGuard.ts` is SEC-D-owned. Proposed patch (after `const background = …`):
```ts
// SEC91-W2A-4 observe: interactive call the guard still treats as background.
const observed = !userId && ctx.background === undefined ? rc.authPrincipal?.userId : undefined;
if (background && observed && limits.burstUserPer10s > 0) {
  try {
    const burst = await checkLayer('ai:obs:burst:user', observed, limits.burstUserPer10s, 10);
    const perMin = await checkLayer('ai:obs:rl:user:min', observed, limits.userPerMin, 60);
    if (!burst.allowed) countWouldBlock('burst_user', operation);
    if (!perMin.allowed) countWouldBlock('user_min', operation);

// countWouldBlock = recordRawCounter('ai.guard.would_block', 1, { layer, operation })
```
Separate `ai:obs:*` key prefixes keep enforcement counters clean. It adds two limiter operations per interactive gateway call, so consider the Upstash daily-command cap (sample, e.g. 10%, or use the per-process in-memory fallback) before shipping.

### 7.2 W2A-1b residual — campaign activation rights (product decision)
Today every campaign-authoring role (admin, creator, reviewer, publisher) can `PUT status: 'active' | 'paused' | 'cancelled'`. The capability registry reserves CAMPAIGN_EXECUTE for COMPANY_ADMIN / SUPER_ADMIN, which argues that activation (and possibly cancel) should be admin-only. Proposed matrix, to be decided by the product owner: edit name/description/dates — admin, creator, reviewer, publisher; pause — admin, publisher; resume/activate and cancel — admin only; delete — admin only (implemented).

### 7.3 W2A-5b — campaign-level roles (product decision)
`requireCampaignAccess` treats every active member as COMPANY_ADMIN, so `campaign_user_roles` and `CAMPAIGN_RBAC_MODE` (default `HYBRID`) are never enforced for members. Removing the fast path today would 403 every non-admin member who has no `campaign_user_roles` row on ~100 routes. Decide per role: (a) keep company-wide access for content roles (document `CAMPAIGN_RBAC_MODE` as inert), or (b) backfill `campaign_user_roles` for existing members, then have the fast path use the real role (`assertTenantAccess(...).access.role`) so `resolveEffectiveCampaignRole` applies, and VIEW_ONLY becomes read-only on campaign routes.

### 7.4 W2A-5d — content lifecycle transitions (product decision)
Proposed matrix, derived from `PERMISSIONS` (`rbacService.ts:48-49`) and the lifecycle spine (`lib/content/contentLifecycle.ts`): create at `draft` / `generated` / `edited` — CREATE_CAMPAIGN roles; `quality_reviewed` / `approved` / `adapted` — APPROVE_CONTENT (reviewer, admin, super admin); `scheduled` / `published` — PUBLISH_CONTENT (publisher, admin, super admin); `archived` and restore — admin. Enforce it in `POST /api/content` (initial `lifecycleStatus`) **and** `POST /api/content/:id/status` together, otherwise the second route bypasses the first.

## 8. Remaining limitations
- `enforceCompanyAccess` still admits an **invited** COMPANY_ADMIN into a suspended company (TenantGuard returns STALE_MEMBERSHIP before it reads the org, so the invited-admin fallback runs), contrary to its own doc comment. `requireCampaignAccess` keeps parity (no org check on the invited path).
- `/api/ai/generate-content` types other than `campaign_content` (`content_pillars`, `weekly_plan`, `daily_plan`, …) still answer without authentication. They return static demo payloads or placeholder errors with rule-based refinement (`languageRefinementService` is "Rule-based only (no LLM)"); no DB read, no provider call.
- `requireCampaignAccess` costs one extra `companies` read on the member path.
- The governance runtime stays off by default; its review-role vocabulary (`brand_manager`, `legal_reviewer`, `creative_director`) has no company-RBAC mapping, so those approvals remain unreachable until the product defines one.
- W2A-2 does not expire the nonce (§6.3). A nonce issued by `register` stays valid until it is exchanged, the registration is re-registered, or it is revoked.
- W2F-1a: an activity id that resolves to no row (including non-uuid execution ids, which the uuid `id` comparison makes the writer reject) still generates and bills without persisting, exactly as before; only the write is withheld. When no exact row-id matches and several rows share the execution id, the first one owned by the authorized company is used.
- The full unit regression was taken before the W2F-1a/1b commits; those two changes were covered by every unit suite that references the changed modules (§3), not by a second full run.
- All tests are hermetic (faked DB and identity provider, stubbed AI/billing sinks); nothing was verified against production.
