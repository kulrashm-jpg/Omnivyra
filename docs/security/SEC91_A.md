### A6 decision (authenticated 403-vs-404) — INTENTIONALLY ACCEPTED
`requireCampaignAccess` keeps 403 for "campaign exists, you are not a member of its company" and 404 for "no owner". Reasons: (1) it is the platform-wide vocabulary — `requireTenantAccess` (403 NOT_A_MEMBER vs 404 ORG_NOT_FOUND), `requireCampaignTenantAccess`, `content/index` CROSS_TENANT_CAMPAIGN — so changing one primitive would not remove the oracle class; (2) only an authenticated caller reaches it; (3) it reveals only whether a random v4 UUID exists, never data; (4) CAMPAIGN-RESOURCE-AUTHZ-SEC-001 deliberately pins it. `enforceCompanyAccess` must keep allowing unknown ids (creation flows). The *anonymous* oracle (strictly worse) is fixed (A6-b).

## 6. Cross-workstream proposals (not applied)
1. **SEC-F — gate blind spot: re-exported route handlers are never gated.** `check-route-auth.js:isRouteFile` tests `/export\s+default\b/`, so `export { default } from '…'` routes are classified as *helper modules* and skipped: `pages/api/activity-workspace/content.ts`, `analytics/v1/system-state.ts`, `command-center/creator-content/generate.ts`, `intelligence/snapshot.ts` (4 of the 14 "helpers"). All four currently authenticate inside the re-exported handler (verified), but a regression there would not fail CI. Proposal: treat `export\s*\{[^}]*\bdefault\b[^}]*\}\s*from` as a route and follow the delegation into the target module (allow `backend/services/**` targets for this re-export shape only).
2. **SEC-D — `pages/api/ai/generate-content.ts:31-44`**: campaign owner looked up before authentication (anonymous existence oracle, same shape as A6-b) and via an unordered `.limit(1)` version row. Proposal: `resolveUserContext` first → 401; use `resolveCampaignCompanyId`.
3. **SEC-B — `pages/api/community-ai/connectors/utils.ts` `requireManageConnectors`**: the SSR-cookie fallback resolves `users.id` by `supabase_uid` without the lifecycle checks the canonical resolver applies (deleted / suspended / revoked session). Proposal: drop the fallback — `getSupabaseUserFromRequest` already reads the `@supabase/ssr` cookie — or route it through `resolveAuthenticatedUser`.
4. **Owner of `backend/services/wordpressPluginService.ts`**: (a) `revokeWordPressPlugin` / `recordWordPressPluginHeartbeat` update by registration id alone — add an optional `companyId` / require a token inside the service so no future caller can repeat A4-b/A1-a; (b) `exchangeWordPressPluginToken` never clears `auth_nonce_hash`, so the "single-use" nonce can re-mint tokens until the next register.
5. **SEC-C (migration)**: `scheduled_posts` has no `company_id`; A2-e is closed only for posts whose social account carries a company. A `company_id` column (backfilled from `social_accounts`/campaigns) would close the legacy remainder.
