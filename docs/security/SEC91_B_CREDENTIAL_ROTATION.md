# SEC91-B3 — Credential rotation runbook (MANUAL OPERATION REQUIRED)

**Workstream:** STEP 3AH-91 SEC-B · **Finding:** B3 (P1) historically leaked credentials · **Status:** MANUAL OPERATION REQUIRED — nothing in this document was rotated, revoked or tested by the agent. No secret value appears here, and none may ever be added.

## Why this exists

The repository is **public** (GitHub `kulrashm-jpg/Omnivyra`) and its history — including `refs/pull/*`, which cannot be rewritten without GitHub Support — contains live-format credentials committed in `.env.local`, `.claude/settings.json` and `.claude/settings.local.json`. The 2026-09-14 read-only P0 exposure audit found these values at hundreds of public ref tips and recorded an **actual harvesting attempt** (a 401 on 2026-09-12 from an automated client using a leaked Supabase JWT). Every credential below must be treated as known to third parties until it is rotated **and** the old value is shown to be dead.

Code cannot fix a leaked credential; only the provider can revoke it. This runbook lists every credential class, where to rotate it, why, and how to verify — in the order to do it.

**Evidence basis:** the brief for STEP 3AH-91 and the 2026-09-14 P0 exposure audit record (hosts, IDs and dates only). The agent had no network or production access and re-verified none of it.

## Rules for whoever executes this

- Rotate at the provider **first**, update the consumers **second**, revoke the old value **last** (after the new one is confirmed working) — except where noted ("revoke immediately").
- Never paste an old or new value into a chat, ticket, commit, log or AI tool. Compare values only locally (for example, a hash comparison in a local shell).
- Consumers: Vercel project `omnivyra` (Production, and Preview if set), Railway service (worker), the Super Admin provider-accounts / `platform_oauth_configs` UI (encrypted DB storage), and any local `.env.local` (never committed).
- After each item, record date, operator, and the verification result in the release log.

## Signing secrets that are now load-bearing (do not rotate casually)

SEC91-B1 removed the unsafe fallbacks, so production now signs with exactly these (names verified present in production):

- `AUTH_SECRET` (Vercel and Railway) — extension session tokens, the per-session request-signing secret derived from them, extension claim codes, and RPA auth-bootstrap tokens. Rotating it immediately invalidates every issued extension session (users re-pair the extension) and in-flight RPA tokens (30-minute TTL).
- `INVITATION_TOKEN_SECRET` (Vercel and Railway) — invitation tokens. Rotating it invalidates every outstanding invitation link (7-day TTL); resend then answers `TOKEN_REBUILD_MISMATCH`.
- `ENCRYPTION_KEY` (Vercel and Railway) — AES-GCM at-rest encryption of tokens and credentials, and (domain-separated since SEC91-B7) the OAuth-state HMAC. **Never rotate without a re-encryption migration.**

Optional hardening, with no deploy dependency: provision dedicated `EXTENSION_SESSION_SECRET`, `RPA_AUTH_SECRET` and `OAUTH_STATE_HMAC_KEY` in a planned window. Each is picked up automatically in preference to `AUTH_SECRET` / the derived `ENCRYPTION_KEY` key, and switching invalidates only that token family.
