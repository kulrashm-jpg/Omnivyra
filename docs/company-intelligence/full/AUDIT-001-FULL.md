# AUDIT-001 — Architecture & System Discovery (FULL EDITION)

> **Archival Full Edition.** Preserves the complete discovery detail. The maintained, authoritative version is the Reference Edition: [`../architecture/AUDIT-001.md`](../architecture/AUDIT-001.md). Frozen at ratification (constitution v1.0). Findings are certified facts; corrections occur only through [amendments](../amendments/README.md).

**Method:** four parallel read-only exploration passes (frontend, API layer, backend services, database + consumers), synthesized. All claims anchored to `file:line`.

**Verdict: Highly Coupled** (with well-designed islands).

---

## 1. Executive Summary

The Company Profile is one of the largest single features in the codebase: ~8,600 lines of frontend across 13 files, 23 API routes under `pages/api/company-profile/` (plus 2 onboarding routes that seed profiles), a ~3,265-line backend service fragmented across a 5-file barrel chain, an 18-file sub-module directory (`backend/services/companyProfile/`, ~4,900 lines), and one wide table (`company_profiles`) that also serves — via `report_settings` JSONB — as the storage substrate for website fingerprints, knowledge versions, crawl metadata, and provenance.

The dominant architectural pattern is **"one giant object, threaded everywhere."** On the frontend, a 2,384-line data hook owns ~60 `useState`s and returns a ~230-key object; a 789-line controller hook re-expands it to ~290 keys; the result is prop-drilled and fully destructured in every section component. On the backend, the service barrel was split by line count rather than responsibility, with near-circular imports resolved only through the barrel, and a read function (`getProfile`) that can silently invoke the LLM and write the database. At the data layer, the table has no foreign key to the tenant root, a TEXT/UUID type mismatch on the tenant key, and a multi-writer JSONB grab-bag with no concurrency control.

The system is mid-migration toward a canonical read model; the newly landed Company Knowledge Graph (commit 52305785) is a third "source of truth" adopted so far by exactly one endpoint. This is the through-line of the entire audit series: new authorities are built, but adoption is incomplete, and the periphery remains ungoverned.

## 2. Frontend Architecture

**Entry points & routes.** The profile UI is reachable at `/company-profile` (`pages/company-profile.tsx`, 307 lines), which calls `useCompanyProfileState()` and renders `CompanyProfileForm`, `ProblemTransformationPanel`, refinement history, and `CreateCompanyModal`. A barrel route `/company-profile-form` re-exports the same form (a second live route). Onboarding deep-links via `?companyId=…&onboarding=company-profile`; a `?ai_refine=1` param auto-starts refinement then strips itself. Navigation enters from `contentNavigationConfig.ts:92`, `commandCenterActions.ts:58`, and several command-center cards.

**Component hierarchy.** Route → `CompanyProfileForm` (`companyProfileFormMain.tsx`, 455) → `useCompanyProfileFormController(d)` → `CompanyProfileFormSectionsA` (543) / `SectionsB` (526) / `SectionsC` (792) + `CompanyStrategyProfileCard` (678, self-contained state + fetches) + six `GuidedChatPanel`s. Support modules: `companyProfileFormSupportA.tsx` (617), `SupportB.tsx` (503), `company-profile.types.ts` (649). Seven files exceed 500 lines; the data hook is 2,384. Header comments reveal the files were mechanically sliced from one original by babel line-range, not decomposed by responsibility.

**State management.** `useCompanyProfileState` consumes `useCompanyContext`, derives role flags, and owns ~60 `useState`s with no reducer: core profile + draft, completion scores, intelligence context, enrichment, refinement history, six guided-chat threads (each panel/messages/input/loading), five "pending save" staging flags, create-company modal state, and onboarding resolution. A security effect clears all server-fetched state when `user.userId` changes (`:174-210`), preventing cross-user bleed. `CompanyContext` (742 lines) owns the auth lifecycle: a Supabase session subscription, an auth FSM, a roster fetch (`?mode=list`) with single-flight + 3-retry + failure-cap, a content-architect cookie fallback, role normalization, and the permission matrix. There is no SWR/react-query/Redux — all data flow is manual `fetchWithAuth` + `useState`. Cross-feature signaling happens through localStorage keys plus a `company-profile-updated` window CustomEvent (`:278-299`).

**Data fetching lifecycle (mount order).** (1) roster `GET /api/company-profile?mode=list`; (2) companyId resolution (URL → selected → single-company fallback); (3) profile `GET ?companyId&includeCompleteness=1`; (4) intelligence-context; (5) intelligence-enrichment; (6) refinements. The strategy card fetches its own strategy + blogs independently. No caching layer; refetch keyed on companyId/auth changes; no manual refresh button.

**Save/update lifecycle.** Pessimistic, full-object, manual-save, not debounced. Field edits call `handleChange` → `updateActiveProfile` (writes to `profile` if present else `draftProfile`). Explicit Save POSTs the entire profile to `/api/company-profile`, recomputes completion, exits edit mode, and fires `notifyCompanyProfileUpdated`. Partial saves exist for brand assets, guidance, intelligence context, problem-transformation, and onboarding presence. Guided chats are staged-optimistic (write into `activeProfile` immediately + `pendingSave` flag, confirm button persists). AI refine strips competitor fields from the payload so AI cannot clobber user-locked competitors, guards double-runs via a ref, and shows a **timer-driven fake progress bar** decoupled from the actual request.

**Loading, errors, validation.** Loading shows plain "Loading profile…" text — no skeletons. A single shared `errorMessage` banner; several fetches fail silently to `console.warn`; `lastFetchStatus`/`lastFetchError` are captured but never rendered. Retry/backoff exists only in `CompanyContext.refreshCompanies`. Validation is limited to canonical-website validation (the gate for AI refine), URL normalization on blur, and brand-asset type/size/squareness checks — no schema or form library; most text fields save whatever is typed.

**AI conversation UI.** Six `GuidedChatPanel`s each drive a distinct endpoint (target customer, campaign purpose, marketing intelligence, competitor, context intelligence, problem-transformation), plus a problem-transformation Q&A panel, one-shot marketing-intel generation, Wikidata facts lookup, enrichment run/review, and strategy-card regenerate.

**Smells (identification only):** god hook (2,384 lines, ~60 `useState`s, ~230-key return); massive prop-drilling of one mega-object (identical ~70-line destructures across SectionsA/B/C); duplicated entry points / double hook instantiation; verbatim-split coupling (files sliced by line range, importing the controller only for its `ReturnType<>`); a dead `CompanyProfileChatPanel`; duplicated fetch/save logic (brand-asset save hand-rolls a POST; five guided-chat send handlers repeat the same scaffold); fake progress decoupled from the request; hidden coupling via localStorage/CustomEvent; mixed responsibilities in the controller (derived selectors + image processing + guidance persistence + JSX-returning render helpers); captured-but-unused diagnostics; auth/role logic split between context and hook.

## 3. Backend Architecture

**API layer.** Every route wraps `createApiRoute` (`lib/platform/routeFactory.ts:89`) — observability + error-classification only, no auth/rate-limit/validation. The dominant tenant guard is `resolveCompanyAccess` (content-architect bypass → Supabase user → super-admin → role check). A strictly stronger `enforceCompanyAccess` (membership + org soft-delete + retryable 503) is used by only one endpoint (`mission-context`). No route-level rate limiting, credit checks, or `aiRequestGuard` on any company-profile AI endpoint — the only rate limiting in scope is on `setup-company`.

**Endpoint inventory (23 + 2).** `index` (GET list/single + POST save; bespoke auth for list mode), `context`, `refine` (AI), `refinements`, `strategy`, `guidance`, `completeness` (**dead**), `mission-context` (**dead**, only `enforceCompanyAccess` user), `forced-context` (**dead**), `intelligence-context` (role-gated POST), `intelligence-enrichment` (AI + crawl, role-gated), `suggest-competitors` (AI), `company-facts-lookup` (Wikidata), `onboarding-presence`, `problem-transformation`, `problem-transformation-questions`, `infer-problem-transformation` (AI), `define-problem-transformation` (AI + deterministic fallback), `define-target-customer` (AI, only KG adopter), `define-marketing-intelligence` (AI), `define-context-intelligence` (AI), `define-campaign-purpose` (AI), `generate-marketing-intelligence` (AI + audit_logs write), plus `onboarding/setup-company` and `onboarding/company-provenance`. There is no shared conversational engine — the six `define-*`/chat endpoints each hand-roll auth, AI, parse, and loop. KG adoption is 1-of-6. Three endpoints are apparently dead (no frontend consumer): `completeness`, `mission-context`, `forced-context`.

**Service layer.** The "main service" is a 5-file barrel chain (~3,265 lines) split to keep files "under 500 lines," each real file repeating an identical ~130-line import/re-export preamble, with `Rest1Enrich` and `Rest1Rest2` mutually importing through the barrel (near-circular). 60+ files import the aggregate. The genuine sub-modules live in `backend/services/companyProfile/` (18 files): types, normalization, extraction schema (zod), refinement prompts, business classification (817 lines, deterministic), entity archetype, problem transformation, strategy/marketing drafts, governance, provenance helpers, competitor domain filter, and `companyKnowledgeGraph.ts` (317 lines, fully deterministic, one caller).

**Read paths (three coexist).** Legacy `getProfile` (Pulse.ts:720) wraps a raw select but carries hidden side effects — `autoRefine` (staleness-triggered LLM refine on read, ≥7 days) and `languageRefine` (per-field LLM rewrite on read); the code's own comments flag this hazard. Canonical `getCanonicalProfile` (adapter:300) overlays deterministic Canonical Context onto empty fields only, governed by a 3-mode flag (off/shadow/enforce; default off = byte-faithful legacy). Raw `supabase.from('company_profiles')` is scattered across ~52 files.

**Write paths (four seams).** `saveProfile`→`upsertCompanyProfilePayload` (guarded `ownedDbTable`, 8-attempt schema-cache column-drop retry); the AI refine pipeline `runProfileRefinement` (crawl → change detection → refresh gate → LLM extraction → classification → competitor discovery → strategy/marketing drafts → upsert → audit → knowledge version + orchestration event); field-specific writers; and raw-supabase deterministic writers (bootstrap, incremental-metadata) that bypass `saveProfile`'s classification/lock logic.

**AI seam.** Single gateway `runCompletionWithOperation` (gpt-4o-mini, temp 0, JSON mode). The crawl pipeline (`crawlWebsiteSources` → fingerprint → refresh gate → LLM chain) governs whether the AI chain runs at all. No dedicated cron re-refreshes profiles; refresh is lazy (staleness on read) plus event-driven.

## 4. Database Architecture

**Tables.** `company_profiles` (one row per company, ~60 columns across identity, commercial, marketing, problem/transformation, socials, confidence, plus `report_settings` JSONB); `company_profile_refinements` (append-only audit, before/after JSONB per refine, **write-only** — no product read path); `companies` (tenant root, UUID); `company_context_enrichment_runs/_suggestions/_review_events` and six firmographic tables (real FKs + CHECK constraints + triggers).

**No dedicated tables** for confidence/provenance/fingerprints/snapshots — all live inside `company_profiles`: `field_confidence` JSONB (per-column bands), `user_locked_fields` JSONB (user-edit wins), and `report_settings` JSONB — a multi-writer grab-bag holding report inputs, `website_fingerprint`, `knowledge_version` + `refresh_history`, `discovered_metadata.provenance`, and `company_facts`. At least five independent read-modify-write writers, no row lock or transaction.

**Constraints/RLS.** Schema is split between untimestamped `database/*.sql` fragments (base table + most columns) and timestamped `supabase/migrations/` (later columns, RLS, satellites) — apply order ambiguous; two columns added in both places. RLS is enabled on `company_profiles` but with only a `service_role_full_access` policy — all backend access uses the service-role key, so RLS provides no runtime tenant isolation; isolation depends entirely on application-level `.eq('company_id', …)` filters. `company_id` is TEXT with no FK to `companies.id` (UUID); company deletion does not cascade. `recommendation_context` is declared TEXT but code stringifies JSON through it. A hand-maintained `COMPANY_PROFILE_FALLBACK_COLUMNS` list mirrors the table (new columns must be synchronized in three places or silently fail to persist).

**Field usage.** No fully-unreferenced columns (352 references across 75 files); the clearest unused surface is the entire write-only `company_profile_refinements` table.

## 5. End-to-End Data Flow

Five flows were traced in full: **Page load** (roster → profile with a possible read-triggered LLM refine → parallel context/enrichment/refinements → sections render); **Manual save** (full-object POST → business reclassification → competitor engine resolution → user_locked_fields computation → upsert with column-drop retry → localStorage marker + CustomEvent broadcast); **AI refine** (crawl → sha256 fingerprint → change decision → 16-branch refresh gate [SKIP/DEFER/METADATA_ONLY/AI] → evidence cleaning → LLM extraction → classification + archetype + competitor discovery → strategy/marketing drafts → `buildRefinedPayload` upsert → refinement audit → knowledge version → orchestration event, with a client-side timer-driven fake progress bar); **Guided conversation** (×6, KG grounding only for target-customer, staged into `activeProfile` then confirmed); **Profile creation** (setup-company → company + role + profile seed rows → crawl → deterministic bootstrap → eager `getProfile(autoRefine:true)` → redirect to `/company-profile`).

## 6. Dependency Map

**Inbound:** auth/tenancy (four models — `resolveCompanyAccess`, `enforceCompanyAccess`, bespoke index-list, server-derived provenance), AI provider (single gateway, no per-route credit/rate guard), internal safeFetch-based crawler + fingerprint/refresh stack, Wikidata (facts + competitor grounding), no profile-owned storage (logo/favicon as URL strings), Supabase service-role client (two conventions — `ownedDbTable` vs raw). **Outbound:** the profile is the grounding substrate for nearly all generation — `getCanonicalProfile`/grounding appears in 103 files; the adoption registry enumerates 96 grounding consumers; major consumers include `buildContentContext` (all content generation), blog/post/thread/newsletter pipelines, unified content/competitor engines, recommendation and campaign services, creator resolvers, `reportInputResolver`, `companyMissionContext`, `onboardingJourneyService`, `dailyIntelligenceScheduler`, and 40+ API routes. Cross-feature UI refresh depends on the localStorage/CustomEvent broadcast.

## 7. Responsibility Matrix

Leaky at the page (dead prop extraction of ~150 mostly-unused values); god hook at the data layer (server I/O + state + role gating + onboarding orchestration + six chat state machines + localStorage broadcasting); mixed controller (derived selectors + image-processing uploads + guidance persistence + JSX-returning render helpers); acceptable-but-coupled sections (clean presentation but each re-destructures the entire mega-object); mixed API routes (transport + auth + direct DB + hand-rolled AI conversations); mixed barrel service (reads that write and call LLMs; crawl+AI+DB in one function). Good separation: the focused `companyProfile/` sub-modules, the canonical adapter, the refresh orchestrator, and the bootstrap service. Weak: the database delegates integrity (tenancy, FK, JSONB shape) to app code.

## 8. Strengths (worth preserving)

The canonical adapter rollout pattern (one gate, three modes, byte-faithful default, overlay-onto-empty-only, explicit adoption inventory); the refresh gate / change-detection stack (deterministic sha256 fingerprinting, policy engine, token-savings accounting, knowledge-version events); the single AI seam; the `user_locked_fields` + fill-empty discipline honored across layers; the deterministic idempotent bootstrap; provenance without schema (derived at read time; the KG follows the same zero-schema principle, fully deterministic, 18 tests); frontend security discipline (per-user state clearing; single-flight + retry + failure-cap fetch; auth FSM); competitor read/write-time scrubbing; the satellite `company_context_*` schema discipline (real FKs, CHECK-constrained enums, `jsonb_typeof` guards, triggers); the role-based redaction concept; uniform route observability.

## 9. Initial Architecture Concerns (list only)

God hook; mechanical line-count splits (frontend babel slices and the backend 5-file barrel with identical preambles and near-circular imports); high fan-in through opaque barrels; reads with side effects; hidden localStorage/CustomEvent signaling; silent column-dropping upsert; fake timer-driven refine progress; three coexisting "source of truth" models plus a fourth grounding engine for competitors; six conversational endpoints with no shared engine; competitor logic across four files; two chat-panel implementations (one dead); three apparently-dead endpoints; four auth-guard models; role gating on 2 of ~12 write endpoints (COMPANY_ADMIN redaction inconsistent); no rate limit/credit check/`aiRequestGuard` on ~10 AI endpoints; `company_id` TEXT with no FK to a UUID root; non-isolating RLS; `report_settings` lost-update races (≥5 writers, no lock); two write regimes for one table; split partially-duplicated schema sources; an unbounded write-only refinements table; full-object last-writer-wins saves; no retry/error surfacing for several fetches; a drift-prone hand-maintained fallback column list.

## 10. Final Assessment

**Highly coupled**, with deliberate decoupling islands. On the frontend, one state object threaded through three layers means any state change touches five or more files, and the section components are bound to the controller by an inferred `ReturnType<>` contract rather than an explicit interface; seven of thirteen files exceed 500 lines and the data hook alone is 2,384. On the backend, the barrel's mutual imports, 60+ aggregate importers, and a read function with write/AI side effects mean behavior cannot be reasoned about locally; `runProfileRefinement` couples crawl, gating, AI, classification, discovery, and persistence in one ~250-line function. At the data layer, one table serves as profile store, fingerprint store, knowledge-version store, provenance store, and settings store simultaneously, with five writers and no concurrency control — the strongest coupling in the system, because every one of ~96 downstream grounding consumers transitively depends on its shape. The discovery converged across four independent examinations, all surfacing the same structural pattern (mechanical splits of monoliths, multiple parallel authorities, JSONB-as-schema); the picture is complete enough to serve as the certified baseline. A system captured mid-consolidation where new authorities are built but adoption is incomplete.
