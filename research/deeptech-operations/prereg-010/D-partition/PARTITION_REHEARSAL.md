## 5. `frame_hash` ORDER-INDEPENDENCE — the exact condition, both directions

**The condition verified, stated precisely.**

> `frame_hash = hashRecords(frame, 'candidate_id')` (`loadFrame`, `cpg_u1_data.mjs:104`) and
> `canonicalRecords(records, sortKey)` sorts with
> `(a, b) => (a[sortKey] < b[sortKey] ? -1 : a[sortKey] > b[sortKey] ? 1 : 0)` — a comparator that
> returns **0 for equal keys** (`lib/canonical.mjs:17`). `Array.prototype.sort` is **required to be
> stable** by ECMA-262. Therefore the sorted sequence, and so the hashed bytes, is a function of the
> input **multiset if and only if `candidate_id` is unique**. If two records share a `candidate_id`,
> stability preserves their relative **input** order, so a different merge order emits different bytes
> and a different `frame_hash`.

`node order_probe.mjs --instrument $T --dir .` → **exit 0**:

```
DIRECTION 1 — candidate_id UNIQUE
  PASS  candidate_id is unique across the combined frame  224 rows, 224 distinct
  PASS  input row orders genuinely differ
  PASS  frame_hash(forward) === frame_hash(reversed)  2812d45c5784840ee7c28aad0f585ce07607569543e6ed7d696e1ed160564918
  PASS  frame_hash(stride-97 permutation) === frame_hash(forward)  2812d45c5784840ee7c28aad0f585ce07607569543e6ed7d696e1ed160564918
  PASS  canonical bytes identical under all three orders
DIRECTION 2 — candidate_id DUPLICATED
  PASS  both probe rows share one candidate_id  SYN-DUP
  PASS  the two rows are otherwise distinguishable  SYNTHETIC-CO-DUP-FIRST vs SYNTHETIC-CO-DUP-SECOND
  PASS  frame_hash DIFFERS between the two merge orders (order-DEPENDENT)  a45f5affe2f3bd4f45f85cedc3ec2fdb7d5743d023393b7dfdee54a8c5c5e95a vs 94c4ffd1ef40b86ed03102154ae92ebb52d0230bd612f95bda52d169dbe73143
  PASS  the multiset of rows is identical in both orders
order-independence condition verified in both directions
```
